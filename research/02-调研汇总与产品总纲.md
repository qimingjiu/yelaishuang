## 〇、项目命名（2026-09-27 定）

**夜来霜**（yè lái shuāng）

- **出处与意象**：唐人成句——刘禹锡《秋词·其二》「山明水净夜来霜，数树深红出浅黄」；王昌龄《长信秋词》「金井梧桐秋叶黄，珠帘不卷夜来霜」；白居易《分司》「夜来霜厚薄，梨叶半低红」。兼有李白「疑是地上霜」的月色如霜、贾岛《剑客》「霜刃未曾试」的江湖剑意。「夜来」在古白话中又作"昨夜"（孟浩然「夜来风雨声」），暗合深夜对戏的场景。冷、净、有剑气，不甜腻，与宫廷/江湖/仙侠三种题材都搭。
- **查重结论（2026-09-27）**：无同名 GitHub 仓库、无同名软件/App、npm 无 `yelaishuang` 包。仅有一部网络小说《梧桐应恨夜来霜》（书名/角色名，与开源工具不同品类，不构成冲突）。
- **工程命名**：仓库 slug 建议 `yelaishuang`（GitHub org/npm 名可同步占位）；**英文名定 `Overnight Frost`**（2026-09-27 拍板。备选排查记录：Frostfall 与《上古卷轴》著名 MOD 重名；Nightfrost 仅散见论坛 ID，无正式产品）。
- **Slogan 备选**：「夜阑对戏，笔落成霜」／「笔落成霜」／「山明水净夜来霜」（直用成句）。
- **UI 命名体系**：见第九节——戏楼、楼层、戏录等圈内词正式引入；另预留概念名 **觅影塔**、**无尽海**（用途待定，与戏楼并列为核心概念候选）。
- **初始内容**：角色卡与开局剧本改编自作者本人小说**黎棠时《岁除上都雪》**（仙侠·朝堂背景，仙门与人间朝廷并存），存放于仓库 `cards/` 目录，全部全年龄。

## 一、已拍板的产品边界（2026-09-27 确认）

1. **只做 AI RP。** 真人语C/真人社区功能（人设审核流、戏楼、招募板、位分权限体系、积分签到、平台级敏感词管制）全部移出范围，相关调研仅作背景与命名参考保留（见第十五节）。
2. **做平台功能与内置工具，不做内容平台。** 无中心服务器（MVP 阶段）、无官方卡库、无公开广场、无评论排行付费商城。
3. **BYOK（用户自带模型 API）。** 用户自己在设置里填模型 API；API 密钥、聊天记录、人设卡、世界书数据全部存用户本地，平台不碰、不存、不中转用户生成内容。
4. **未成年与 NSFW 的解法 = 分发形态 + 社区约定（2026-09-27 复核确认）：**
   - **代码只写一份，PWA + Tauri 是唯一分发姿势**：Web 应用做成 PWA（浏览器里就能"安装"成应用），Tauri 套壳出桌面安装包发布到 GitHub Releases。**用户体验不依赖第三方打包工具**，不用"网页转应用"类服务；仓库自带 Tauri 打包配置，用户想自己构建也可以。
   - 想玩就自己下载安装包或安装 PWA，自取自装。
   - 合规逻辑：服务器不碰用户内容 → 内容平台审核义务整体消失，身份 = 开源软件作者，适用 GitHub 条款；私密生成内容归用户与其模型服务商之间的协议（各家 usage policy）。
   - **仓库红线：仓库内不放 NSFW 内容**——软件本身是工具没问题，但仓库内容（README、示例卡、内置模板、截图、issue）会被 GitHub 条款处理，全部保持全年龄；release 页面写明年龄提示。
   - **社区约定，不强制**：`CODE_OF_CONDUCT.md` 照 GitHub 惯例写，另加社区约定页，约束范围 = 仓库社区言行（issue/discussion）+ 官方随附内容。不约束、也无法约束用户的私密使用。
5. **卡生态：不做官方卡库。** 编辑器原生支持 Character Card V2 导入导出（含 PNG 嵌入），借力 Chub 等既有卡站生态。
6. **未来决策点**：若日后加官方卡库/剧情广场/云同步，平台义务整体回归，届时启用"公开区严格 SFW + 私密本地自理"框架。

## 二、目标用户与玩法入口

**用户画像**：语C/古风演绎背景玩家（懂皮、戏录、雷点，重古风语感与资料工具）+ AI RP 玩家（重角色扮演质量、记忆、可控性）。语C 用户以 14–25 岁为绝对主体，两大初衷是演绎创作与交友。

**两种玩法，同时留入口**：

| 玩法 | 玩家实际做什么 | 首版实现建议 |
|---|---|---|
| 与一位角色对戏 | 与某位官员、游侠、仙门弟子长期互动 | 默认入口，提供角色卡和数个不同开局 |
| 进入一个故事世界 | 玩家拥有身份，AI 同时承担旁白和必要配角 | 以场景/剧本开局，明确当前在场人物与玩家目标 |

依据：Character.AI 将角色与 Scenes 分开；AI Dungeon 用可复用 Scenario 开启独立 Adventure。

## 三、内容对象模型

六个对象分开管理，不当一锅炖：

| 对象 | 示例 | 回答的问题 | 为什么单独管理 |
|---|---|---|---|
| 世界 | 大晟宫廷、澜州江湖、某修仙世界 | 制度、地点、规则是什么 | 共享制度、地图和能力规则 |
| AI 角色原型 | 一位调查官、镖师、剑修 | AI 扮演谁、为何这样行动 | 同一人物可参与多个故事；原型稳定，修改应保留版本 |
| 玩家身份 Persona | 证人、行商、外门弟子 | 我在故事里是谁 | 每个故事可不同；"现实中喜欢什么"与"这局是怎样的人"分开存 |
| 场景/剧本 | 雨夜来访、失镖追踪、入门试炼 | 从哪里、什么时刻、什么冲突开始 | 同一组人物可反复从不同情境开局 |
| 故事存档 | 用户某次游玩 | 这条线实际发生了什么 | 当局关系与事件不能写回原始角色卡 |
| 剧情分支 | 接下委托/拒绝委托 | 分支后的世界 | 各分支的事件、摘要、状态相互隔离 |

**默认流程**：选题材 → 选角色或剧本 → 选我的身份 → 看开场与玩法 → 开始对戏 → 自动保存 → 继续或从某节点分支。

**版本规则**："开始新故事"与"继承旧故事记忆"是清楚的两个选项；修改角色原型后旧存档保留原版本，是否升级由使用者决定，避免人物突然换性格。

## 四、人设卡体系

### 4.1 "格式"分三层，不混在一个菜单里

| 层次 | 常见形式 | 网站呈现 |
|---|---|---|
| 内容写法（人如何写） | 自然语言、字段文本、Markdown、YAML、XML、W++、PList、Ali:Chat | 普通用户用中文表单；高级用户自由编辑 |
| 交换协议（软件如何理解） | Character Card V1 / V2 / V3 | 导入时识别版本，显示支持范围 |
| 文件容器（数据如何携带） | JSON、含元数据的 PNG；V3 另定义 CHARX | 导入导出 + 完整性提示 |

注意：写法标签（W++ 等）不能据格式名推定模型表现；支持读取某版本 ≠ 支持其所有扩展行为。

### 4.2 Character Card V2（基线标准）

顶层信封 `spec: 'chara_card_v2'` + `data` 包裹；顶层同时复制一份 V1 扁平字段做垫片。**V2 PNG 仍是分发标准**（V3 = CharX 容器 = ZIP，RisuAI 主推，按实际完成度逐项声明支持）。PNG 嵌入原理：JSON→base64→写入 PNG 的 tEXt chunk（keyword=`chara`），大卡用 zTXt 压缩 chunk（2MB 上限）——立绘即卡，分享图=分享角色。

| 字段 | 要点 |
|---|---|
| name | 角色名，同时是 {{char}} 宏展开值 |
| description | 主定义，**永久 token** 每条注入，越靠底部权重越高；放身份、外貌、经历、动机、行为与能力限制 |
| personality | 性格摘要，永久 token；精炼性格与冲突，不重复整份 description |
| scenario | 情境，永久 token；只放"永久为真"的设定，不写每天变化的位置伤势 |
| first_mes | 首条开场白，临时 token；**模型从这里学的文风/长度最多**，想回多长写多长；给玩家留回应空间 |
| alternate_greetings | 多开场白数组，前端 swipe 切换 |
| mes_example | 示例对话，`<START>` 分隔，临时 token；锁声线防漂移；至少含一次拒绝/冷场示例；必须手写不能粘 AI 生成 |
| system_prompt | 非空时替换全局系统提示，须支持 {{original}} 占位符；**"不代写 {{user}} 行为"的铁律写在这里，用正面措辞** |
| post_history_instructions | 替换全局 UJB，同上 |
| creator_notes | 仅供使用者阅读，不进提示词（POV 声明、内容注记、立绘出处、版本号） |
| character_book | 角色专属 lorebook，角色书优先于全局书 |
| tags / creator / character_version | 不进提示词，仅展示/排序/筛选 |
| extensions | 必须命名空间化；导入导出**保留未知键值**（保留 ≠ 实现其功能，未实现能力要提示） |

### 4.3 好卡写法实测（Chub 前 30 星 SFW 卡采样）

- 67% 用纯散文段落，0 张用严格 PList/W++（W++ 已淘汰）；赢家是**混合式**：分主题标签段 + 完整句子——人格经历必须散文（模型需要因果链），可枚举事实（衣着装备技能）才用列表
- 永久 token 目标 **800–1500，2000 是红线**；样本中位 1085
- first_mes 中位 178.5 词，主流 150–350；70% 星号动作体/30% 纯小说体；greeting 多数不以提问收尾，主流是"社交压力动作"开局（角色做出你无法不回应的举动）
- 70% 带 mes_example；lorebook 内嵌仅 20%，动机是**条件揭示**（秘密按名字/话题分层释放）而非省 token
- **编辑器设计启示**：①双视图同一数据（中文表单 ⇄ 纯文本）；②内置古风模板包；③导入导出 V2 PNG + 裸 JSON + V1 垫片，lorebook 编辑器支持 selective/constant/position/概率/递归（酒馆用户迁移的硬门槛）；④**好卡检查器**：永久 token 红线、mes_example 格式检测、是否代写用户行为、scenario 是否永久为真、动词重复检测

### 4.4 创作模板

可直接交给创作者填写的完整模板（角色卡 / 玩家身份 / 世界书条目 / 剧情状态与记忆四套 + "沈砚"完整示例 + 笼统形容改可执行行为的对照表），见《古风AI-RP人设与世界书模板.md》，这些就是**内置模板包的内容基准**。核心思路：

- 好人设要能回答：他是谁、眼下想做什么、为什么不能轻易做到、遇到阻力如何行动、怎样说话、与玩家什么关系、有哪些不知道或不会做的事
- 角色可以撒谎：事件记录区分"角色声称的事"与"剧情已确认的事"；角色不知道的秘密不因别人说过就自动知晓

**三种题材的附加字段**（依附世界，不给每人强制填同一张巨表）：

| 题材 | 值得补充的字段 | 应明确的限制 | 内置模板包建议 |
|---|---|---|---|
| 宫廷/宅门 | 官职位份、宗族支系、公开与私下称谓、婚约、政治依附、通行范围 | 品阶礼制依附所选世界，不能把不同朝代制度混用 | 位份表预置唐制/宋制/清制/通用宫斗制，可自定义；升贬记录入时间轴 |
| 江湖/武侠 | 门派、师承辈分、武器、招式特点、仇怨、声望、负伤 | 能力有距离/体力/伤势限制，秘技不能临时新增 | 境界体系模板库（武侠品级），门派页 |
| 仙侠/玄幻 | 种族、境界、宗门、功法、法器、寿元、禁制 | 境界顺序和突破条件由世界定义，资源代价不能靠叙述抹除 | 经典修仙流/洪荒流层级模板，可自定义+突破条件，与角色卡联动 |

宫斗固设卡传统中的**数值化属性**（帝宠 55%、才艺 85% 等）作为可选表达保留；"好感度"可以是可选，但不宜成为全部关系的唯一状态——政治合作、师门信任、家族责任可能互相矛盾，用关系类型+事件记录更有解释力。

### 4.5 导入导出基线

以 **V2 JSON/PNG 为基线**，识别 V1；V3 按实际完成的字段与容器逐项声明。角色卡、世界书、聊天存档分别导出，另提供可完整恢复的整包备份。导出一个角色 ≠ 迁移了全部故事记忆、世界、模型设置。

## 六、功能清单（P0/P1/P2）

P0=首版核心；P1=核心稳定后增强；P2=玩法扩展。

| 优先级 | 功能 | 首版应交付的具体能力 |
|---|---|---|
| **P0** | 中文角色编辑器 | 草稿自动保存（丢稿=退圈级事故）、基础与高级字段、开场预览、试聊 |
| P0 | 玩家身份 Persona | 创建多个 Persona、绑定当前故事、显示"我现在是谁" |
| P0 | 题材与开局模板 | 宫廷、江湖、仙侠至少各一套能直接开玩的样例 |
| P0 | 聊天控制 | 流式回复、停止、重试、编辑双方内容、重生成、续写 |
| P0 | 基础世界书 | 条目、关键词和别名、常驻、启停、优先级、绑定范围 |
| P0 | 分层记忆 | 关键事实固定、阶段摘要、最近对话；用户能查看和改正 |
| P0 | 简版状态面板 | 时间、地点、在场人物、当前目标、重要关系和物品；允许手动修正 |
| P0 | 存档与分支 | 自动保存、命名存档、从某消息另开路线，状态与摘要随分支保存 |
| P0 | 导入导出 | V2 JSON/PNG 基础兼容、识别 V1、聊天文本导出、完整备份恢复 |
| P0 | 模型与用量 | BYOK 至少一个可靠后端、显示调用失败原因和用量、高级参数折叠 |
| P0 | 可读与可用性 | 手机长文输入、字体行距、明暗模式、长记录浏览与搜索 |
| **P1** | 多 NPC 调度 | 场上名单、指定回应者、进退场、角色知情范围 |
| P1 | 事件与关系管理 | 事件时间线、关系变化依据、伏笔、秘密、称谓提示 |
| P1 | 内容查找 | 按题材、身份、玩法、情绪基调、文风检索角色和场景（本地库） |
| P1 | 创作增强 | 人设矛盾检查、场景灵感、试聊对比、卡片版本差异 |
| P1 | 小说阅读视图 | 对戏记录整理为适合长篇阅读的章节 |
| P1 | 古风工具第一批 | 见第八节标 P1 的工具 |
| **P2** | 深度模拟 | 修炼、经济、战斗、任务状态机、地图、骰子与规则判定 |
| P2 | 多媒体 | 立绘生成、语音、动态背景、背景音乐 |

## 七、对话引擎核心设计

### 7.1 六层上下文

模型每次只收到当前需要的内容，完整聊天另作长期档案：

1. 稳定角色设定（角色卡永久 token）
2. 世界规则（世界书）
3. 本局关键事实（锁定的重要事件/承诺）
4. 当前状态（时间地点人物目标伤势物品）
5. 阶段摘要与可回查事件
6. 最近对话

世界书回答"背景规则是什么"，记忆回答"已经发生过什么"，状态回答"此刻是什么情况"。例："此朝官员进内廷需许可"=世界规则；"玩家替调查官找回账册"=事件；"账册现在在玩家身上"=状态。

### 7.2 世界书机制（SillyTavern 全集为参照）

- 条目：keys（支持正则，key 本身不进提示词）、content（必须自包含）、insertion_order（小=靠前）、priority（预算耗尽时小先丢）、selective+secondary_keys（AND 逻辑）、constant（恒注入）、position（9 档插入位置含 @D 深度注入）
- 触发策略：恒触发 / 关键词 / 向量语义；概率触发；包含组（同组同时触发按权重抽一条→可做随机事件）；时效（sticky/cooldown/delay）；角色过滤器
- 四层绑定：全局/角色/Persona/聊天，可设合并策略
- **中文要点：whole-word 匹配必须关闭**；关键词要考虑中文别称（名、字、职衔可能指向同一人）

### 7.3 记忆

- 自动摘要可能漏细节或幻觉 → 可检查、可编辑、可回退；关键事实可锁定；重要记录带原消息出处
- 区分"角色声称的事"与"剧情已确认的事"；传闻单独记录（内容/说话者/是否证实）
- 长上下文有帮助但不能单凭容量推定记忆可靠（Lost in the Middle，用于设计验证方法）

### 7.4 状态更新

模型提出变化 → 网站校验或让用户确认 → 保存变化及事件依据。纯叙事模式可宽松；若要求精确计算丹药、银两、修为、伤势恢复，用明确规则维护数据。

### 7.5 分支与回滚

编辑、重生成、删除旧情节、切换分支时，相关记忆要回滚或重算；已弃用的回复不能继续影响主线；不同用户、不同故事、不同分支不共用一份不加区分的记忆。

### 7.6 多 NPC 信息边界

共享聊天历史 ≠ 秘密隔离。若剧情要求未在场人物不知道密谈内容，需额外设计人物知识范围（在场名单 + 各角色知情范围）。

## 十、古风资料组织与出处

**原则**：每个世界先选——完全架空 / 参考指定朝代 / 明确声明的混合风格。宫廷、江湖、仙侠只是题材标签，不足以决定统一礼制。朝代与世界标签必须随资料保留；仙侠境界、门派规矩属于作品设定，不能伪装成史实；架空世界可自由设定，但内部要前后一致。

## 十一、技术要点

- **一份代码两种形态**：Tauri 桌面壳（GitHub Releases 发安装包）+ 同一代码的网页版（GitHub Pages，PWA 可安装）
- **CORS 坑（BYOK 前端最先踩的坑）**：浏览器直连各家模型 API 会撞 CORS 墙（部分供应商禁止网页跨域调用）——Tauri 壳用 Rust 层转发解决桌面端；纯网页版内置一个**可选的本地小代理**
- 数据全部本地存储；断线恢复（已发消息、部分回复、输入草稿）
- 流式回复必须做（长戏文体验的关键）

## 十二、开发前验证清单

用实际对话检验核心体验，建议准备宫廷、江湖、仙侠三个可试玩样例：

| 测试场景 | 观察什么 |
|---|---|
| 宫廷：同一人有本名、字与职衔 | 是否识别为同一角色，公私称谓是否稳定 |
| 宫廷：密谈只有两人参加 | 未在场人物是否凭空知道秘密 |
| 江湖：主角受伤后多轮对话 | 伤势是否仍影响行动，而非无解释消失 |
| 江湖：不同门派人物争论 | 是否保持不同立场、语气与知识范围 |
| 仙侠：使用法器与消耗丹药 | 状态是否有依据，物品是否凭空恢复 |
| 长局：早期许诺后经 30/60/100 轮 | 能否召回约定及正确人物，成本与等待时间变化 |
| 重生成与分支 | 被弃用剧情是否从记忆移除，分支是否相互独立 |
| 修改角色卡后继续旧存档 | 是否按指定版本继续，而不是无提示改设定 |
| 手机断线与刷新 | 已发消息、部分回复、草稿能否恢复 |
| 导出后重新导入 | 角色、世界书、关系状态与分支按声明范围还原 |

**评价维度**：人物一致性、古风语感、玩家行动空间、推进能力、事实与状态保持、记忆纠错、延迟、费用。同一模板对多个候选模型评测，保留原始输出，不只挑最好的一段。

## 十三、红线与教训（适用于本项目的子集）

1. **政策反复是头号信任杀手**（Glow 下架、名朋版权下架、JanitorAI 突袭实名、星野静默关功能）→ 对策：官方随附内容全年龄的规则第一天写死并公开；平台不碰用户内容，无可反复之处。
2. **基础设施要稳**（JanitorAI 78% 在线率是口碑崩塌前二原因）→ 本地优先架构天然缓解；网页版要保证 PWA 离线可用基本盘。
3. **功能全≠好用**（ST 驾驶舱反例）→ 渐进式披露：5 分钟出第一个角色（猫箱分步引导为参照）。
4. **用量透明**（星野免费额度断崖教训）→ BYOK 也要显示调用失败原因和用量。
5. **不铸币不抽卡**（Gaia 通胀、星野抽卡吐槽）→ 无平台经济，就没有经济系统翻车。
6. **社区强产品弱会被搬空**（Chub）→ 产品体验优先，卡生态借力不做库。
7. （真人圈"排斥AI文"的情绪属于真人RP语境，本项目不适用；创作增强功能仍定位为辅助而非替代。）
